Record decisions that change the architecture, scope or data model.

| Date | Decision | Reason | Alternatives considered | Approved by |
|---|---|---|---|---|

| 2026-07-24 | Normalise once at the metric layer; the index applies weights only | Prevents double-normalisation when real (already 0-100) Metric Results feed an index; keeps a single source of truth for scaling | Normalising again at each index node (found during the Step 1 integration audit to corrupt scores) | |
| 2026-07-24 | Add a metric-calculation step (answers → Metric Result) and backfill answer_numeric | The Survey→Index chain had no code turning answers into Metric Results; index only read them | Leaving Metric Results to be populated manually / externally | |
| 2026-07-26 | Finding A: a campaign requires an existing Survey Management record (option 2) | educ_sg makes Survey Tracking.survey_name mandatory. Auto-creating a stub would put planning documents nobody planned into the institutional register that this app exists to produce evidence from; relaxing the field via a Property Setter would weaken a constraint educ_sg's own code may rely on. D1 bends: Survey Management stays reference-only for AUTHORING, but is a prerequisite for COLLECTING. | Auto-create a stub; relax survey_name; keep two campaign types | Already enforced by educ_sg + survey_tracking_hooks; the work was making it legible in the UI |
| 2026-07-26 | Lineage is snapshotted onto UCC Score Breakdown at calculation time, not read live | Question Mapping is live and keeps changing. Reading it at report time meant an old result's lineage reshaped whenever someone remapped a question while its numbers stayed fixed - unacceptable for Criterion 7.1.1 evidence, which is shown externally. | Dated caveat on a live read; a separate snapshot DocType | Three Small Text fields, no new DocType. Only helps results calculated after it lands, so the report flags pre-snapshot results rather than showing them as untraceable |
| 2026-07-26 | A shared metric's contribution is repeated per objective, never split | 5 of 265 real questions carry more than one objective. Splitting invents arithmetic that appears in no calculation; attributing to a 'primary' objective silently drops the rest. | Split evenly; pick a primary | Objective sections carry no total, deliberately - no such number exists |
| 2026-07-28 | Conditional display is evaluated in BOTH places, and only the server's verdict counts | Decision V1 recorded the landmine: logic shipped client-side only would let a hidden *required* question block submission, and would let a crafted POST dodge a branch's required check by omitting it. `display_logic.py` is one pure rule; `submit_survey` recomputes visibility from the SUBMITTED answers and enforces `is_required` only on visible questions, dropping answers to hidden ones. The browser copy is presentation. | Client-side only (the landmine); a server-rendered multi-request wizard | Rules fail CLOSED - a rule pointing at a deleted question hides its question rather than stranding respondents behind something unanswerable. Both copies make the same choice, so they cannot disagree |
| 2026-07-28 | Skip To Section and End Survey dropped from the display_logic Select | Neither was ever wired to anything, and under decision V5 (sectioning is a marker question type) there is no section identifier for a skip to target. Removed rather than left as options that silently do nothing. | Designing section targets so the options could work | Reinstate with a real target model if UCC ever asks for skip logic |
| 2026-07-28 | Multi-page uses a "Page Break" question type, not a page field or page doctype | Sectioning already works this way (V5). A page is the run of questions between two markers, so paging needs no schema beyond one Select option and no change to sequence, reorder or answer storage. | A page_number field per question; a UCC Survey Page doctype | All pages submit in one POST - no partial save, which is a separate feature with its own storage question |
| 2026-07-28 | Question layout is one width field on a 12-column CSS grid; no 2D coordinates | CSS Grid derives rows from document order plus each item's span, so the existing 1D `sequence` plus one Select IS a 2D layout. `grid-auto-flow` stays `row`, never `dense` - dense back-fills gaps and would show questions out of their numbered order. | x/y coordinates per question; a row/column container doctype | Mobile collapse is a media query, no JS. Layout freezes at publish like every other question edit |
| 2026-07-28 | No theme editor: the public form's colours are CSS custom properties set once in Website Theme | `/survey` already inherits the site theme via `templates/web.html`; only the form's own controls were hardcoded. One college, one brand - a per-survey picker invites twelve differently-coloured surveys. A staff-editable free-text CSS field on the one guest-reachable page is a stored-injection surface. | Per-survey colour pickers; a raw CSS field; a theme DocType | If ever needed: a closed Select of brand presets with validated values, never a CSS blob |
| 2026-07-28 | A published version's CONTENT is frozen; its PRESENTATION is not | The invariant immutability protects is "every published score must be reproducible", and a score derives from question text, type and choices plus the answers given. `layout_width` feeds none of that - not metric_engine, not index_engine, not mapping, not lineage, not Score Breakdown - so nothing downstream of a question can observe it. Freezing it meant the only way to fix a layout that read badly on a phone was a new version, which orphans the campaign already collecting against the published one. | Leave layout frozen and require a new version (orphans the campaign); an "unlock" flag on the version (a switch that turns immutability off is not immutability) | `versioning.PRESENTATION_FIELDS` is a WHITELIST, never a blacklist: every field added to a question later is frozen by default and exempting one has to be a deliberate act. `presentation_only_change()` returns False the moment anything else differs, including choice ORDER and re-parenting, so the exemption cannot be used to smuggle a content edit through beside a width change. Deliberately ungated and visible - the Inspector shows an Apply Width button on a published version and says why - because adjusting a live survey's layout without spinning a version is the point. Frappe's `track_changes` was already on for UCC Survey Question, so each presentation edit lands in the Version log with its diff at no extra cost. |
| 2026-07-28 | Width is resized by dragging in Preview, not in the Questions list | Preview is the only place in the builder that renders the real 12-column grid, so it is the only place a width handle shows what it is doing. Behind an explicit "Edit layout" toggle so the sheet is never accidentally an editor. | Handles in the Questions list (would put a 2D control in a 1D list and risk the working index-based drag-reorder: "drop between 3 and 4" is unambiguous in a list and genuinely ambiguous in a grid, and a mousedown inside a `draggable="true"` card starts an HTML5 drag as soon as the pointer moves); a blank-canvas designer | Snaps to the four `layout_width` values - there is no pixel width field and there must not be one. Dashboard Studio was believed to have card resize handles to reuse; it has none. The mousedown -> document mousemove/mouseup shape comes from `node_canvas.js:_makeDraggable` |
| 2026-07-28 | No blank-canvas layout designer | CSS Grid already derives rows from document order plus span, so `sequence` (drag-reorder) plus `layout_width` (drag-resize) IS a 2D layout. What a free canvas adds beyond them is holes - empty cells, which in a questionnaire read as "something failed to load" - and visual order differing from document order, which is an accessibility regression: screen readers and keyboard tab order follow DOM order, so a respondent using either would traverse the form in an order contradicting both the visual layout and the numbering. Same reason `grid-auto-flow: dense` is banned. | A canvas with per-question row/column/span (~400-600 lines, a second layout path in survey.html, and a permanent second way to express layout) | Any future design surface writes STRUCTURED fields only. `www/survey.html` is the only guest-reachable page in this app: a staff-editable HTML/CSS blob rendered there is stored injection (CSS exfiltrates via attribute selectors and `url()`; a `</style>` escapes the block and becomes XSS on the page collecting real responses, against an anonymous respondent). Colours are matched against `^#[0-9a-f]{6}$`, fonts come from a closed list |
| 2026-07-28 | One renderer for the respondent form: `public/js/survey_form.js` + `public/css/survey.css`, shared by `www/survey.html` and the Builder's Preview | Preview was a parallel implementation - its own per-type widget switch, its own grid renderer, its own copy of the page-split rule and ~50 lines of `.ucc-sb-*` CSS shadowing `.ucc-*` - which is why it needed the duplicate pagination and still could not show real styling. The earlier "no new external JS bundle on the guest path" constraint was about third-party libraries (survey-core), not our own assets. | Keeping two renderers in sync by hand (the check_repo guard that watched the duplicated page-split rule was the cost of this, and is now deleted); a third-party form library | SUBMISSION IS NOT IN THE SHARED MODULE: the fetch, the CSRF header and the form-encoded body stay inline in `www/survey.html` and arrive as `opts.onSubmit`, so the guest submission path is unchanged and unreachable from the Desk. No `onSubmit` → no submit button. Assets load per page via `context.include_js/include_css` with BUNDLE names, never raw `/assets/…` paths (one-year cache; already caused a stale-asset bug here) |
| 2026-07-28 | A preview route, `/survey?preview=<version>`, gated by a SEPARATE function rather than a flag | Authors need to see a Draft, which by definition has no campaign and no token. Two functions - `public_survey_payload(token)` with the four anonymous gates, `preview_payload(version)` with logged-in + read permission - because a shared function with an `is_preview` flag is how unpublished content eventually reaches a guest: one wrong caller and the gate inverts. Two functions cannot be called wrongly. | A flag on the existing payload function; a second www page duplicating the template; an anonymous preview token | The preview gate is strictly STRONGER than the anonymous one and relaxes exactly one thing: content need not be Published. It relaxes nothing about writing - preview renders with an empty token and `submit_survey`'s first act is to resolve one. `submit_survey` has no preview parameter and no preview branch, and `check_repo.sh` now fails if it grows one |
| 2026-07-28 | Layout editing moves from Preview into the Questions panel; Preview is pure preview | Direct manipulation belongs where the questions are managed, and Preview's job is to be the real page. The two objections to a grid in the Questions panel both resolved: reorder already means "drop onto card N, take its slot" (not "between"), which is equally well-defined in a grid since the sequence stays linear and CSS Grid only decides where it wraps - so `_wireQuestionDrag` and `_reorder` are unchanged; and the mousedown-vs-`draggable` collision is fixed by turning `draggable` off for exactly as long as the width grip is held. | Insertion indicators computed from pointer position, and moving `draggable` onto the ⋮⋮ handle - both rejected for changing verified reorder behaviour for a cosmetic gain | Drops stay CARDS-only, so row gaps are not drop targets. The 2D rendering is a CSS change, not a handler change: the revert is one line back to `display:flex`. The panel shows PROPORTION, not the respondent's real line lengths - Preview is where accuracy comes from |
